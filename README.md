# ADA - MP-1 Editor

A free, open-source (GPL-3.0) editor and librarian for the ADA MP-1 MIDI Programmable Tube Preamp. It runs in the browser (Chrome or Edge, via Web MIDI) on Windows, macOS and Linux.

The MP-1 must run **Level 2 (v2.x) firmware**. At power-up the display shows "ADA" and then a three-digit number, and the first digit is the software level. Level 1 units (for example v1.38) don't respond to SysEx, so no editor can read or write them.

> **Unofficial and not affiliated with, endorsed by or supported by ADA Signal Processors, Inc.** "ADA" and "MP-1" are used only to identify the hardware this editor works with. The project uses none of ADA's logos or artwork. All trademarks belong to their owners.

## Reference manuals

The MP-1 manuals are published by ADA Signal Processors, Inc. and are not redistributed here. For local development, put the PDFs in the repo root, where `.gitignore` excludes them.

## Protocol harness

A command-line tool (Node 20+) that questions a real MP-1 over a USB-MIDI interface, so the protocol can be confirmed against the hardware (see `docs/adr/0002-hardware-is-protocol-source-of-truth.md`).

```sh
npm install
npm run harness -- --list-ports
npm run harness -- [--probe <name> | --all] [--in "<input port>" --out "<output port>" --channel 1] [--timeout 3000] [--dump-timeout 15000]
```

Without `--in`, `--out` and `--channel`, the harness lists the ports and asks for them and the channel. It remembers the choice and offers it as the default next time. Each session starts by asking for the firmware version from the power-up display, and warns if it isn't v2.x.

The default probe, `connectivity`, requests the Working Register and prints the eleven raw parameter values, or explains why no valid reply arrived. `--probe memory-image-dump` requests the full Memory Image, rejects a reply that is truncated, too long or fails its checksum, and reports how long the dump took. A valid Memory Image is saved as the session's backup: `memory-image-1.syx` holds the reply exactly as received, and `memory-image-1.json` decodes it into 128 Programs in Memory order. The dump gets its own, longer wait (`--dump-timeout`, default 15000 ms). `--probe documented-commands` sends the manual's Get/Set Parameters (07/06) messages to the Working Register and records any reply. It sets Master Gain in the Working Register to 0; recall the program to restore it. `--probe working-register-write` writes a known Program to the Working Register, reads it back and lists any parameter that differs. `--probe voicing-master-gain` sets a non-zero Master Gain, changes Voicing over SysEx and reports whether Master Gain was reset to 0, as it is when Voicing is changed on the front panel. Both read the Working Register first and write that Program back at the end, and neither writes a Memory. `--all` runs only the probes that leave the unit as it was (connectivity and memory-image-dump), so it skips the three that change the Working Register. `npm run harness -- --help` lists the probes.

Nothing writes Memories unless the session has a verified backup. `--probe memory-image-load`, `--probe protect-on-load`, `--probe direct-memory-write`, `--probe load-pacing` and `--restore <file.syx>` therefore run `memory-image-dump` first and are refused, sending nothing, if it fails. Before each write the harness asks for confirmation, showing how many of the 128 Memories a Memory Image load will change, and then asks you to set Protect OFF (Store, then Bank+8). `memory-image-load` loads the backup with its Memories rotated by one, dumps it back and lists every Memory that differs, then loads the backup back and checks it. `protect-on-load` asks you to set Protect ON instead (the same Store, then Bank+8), loads the same rotated image and dumps it back, and records whether the unit stayed silent, answered with an error, or wrote some or all of it; if any Memory changed, it asks you to set Protect OFF and loads the backup back. `direct-memory-write` sends a Program with the Working Register set command (09) addressed to Memory 2 instead of `7F`, first as 0-based (`01`) then as 1-based (`02`), confirming each write; a dump after each shows which Memory changed, if any, and a Working Register read shows whether the Program landed there instead. Afterwards the Program that was sounding is written back and the backup is loaded back. `load-pacing` finds how to pace a Memory Image load through your USB-MIDI interface: it sends the load in chunks of each `--pacing-chunks` size (bytes, or `whole`; default `whole,256,64`) with each `--pacing-delays` pause between chunks (default `0,10,50` ms), `--pacing-repeats` times per setting (default 3), and checks every load with a dump. Loads alternate between the rotated backup and the backup, so a lost load never reads as a success. One confirmation and one Protect OFF cover the whole series. The report lists each setting's success rate and names the fastest one that never failed, or says none was reliable; the backup is then loaded back with that setting if the unit doesn't already hold it. If it is stopped part-way, the backup is loaded back in the same chunks as the last load that read back correctly. `--restore` loads any saved Memory Image, such as a session's `memory-image-<n>.syx`, and checks it with a dump; a restore that reads back correctly becomes the session's new backup, and one that doesn't is undone. Ctrl-C stops the running probe and loads the backup back where needed; press it again to quit at once.

`--calibrate <parameter>` runs guided Display Value calibration of one parameter (`overdrive-1`, `overdrive-2`, `master-gain`, `bass`, `midrange`, `treble`, `presence`, `effects-loop`, `chorus-depth`, `chorus-rate` or `voicing`). It sets the parameter to each raw value in turn through the Working Register and reads it back. For each value you press EDIT, then the parameter's button, type what the display shows, and press EDIT again (the unit ignores MIDI during an edit). Type `s` to skip a value, `r` to set it again, or `b` to go back to the previous one; at the end you can redo any entry by its raw value. Effects Loop and Voicing also get values past their range (Effects Loop 2, 64 and 127; Voicing 3, 64 and 127), so the report records what the unit does with them. Each entry is saved at once to `--calibration-file` (default `harness-sessions/calibration.json`), so an interrupted calibration resumes where it stopped, in this session or a later one. The result is a table of raw value → Display Value, with every disagreement with the manual's tables marked. No Memory is written, and the Program that was sounding is written back afterwards; if you stop with Ctrl-C, recall the Program on the unit instead.

Each session writes to a new folder under `harness-sessions/` (ignored by git): `capture.log` has every MIDI message sent and received, timestamped, byte by byte, and `report.json` has the firmware version and each probe's verdict and evidence.

Run the harness from Windows, macOS or native Linux. WSL2 can't see USB MIDI devices.

Development: `npm test` runs the tests (no hardware needed) and `npm run typecheck` checks types. `src/core` must stay framework-free with no Node-only dependencies, so the browser app can reuse it; its own typecheck config has no Node types to enforce that.
